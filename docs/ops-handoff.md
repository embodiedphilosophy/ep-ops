## 1. What the dashboard is for

One place for EP staff, contractors and rotating teachers. Every screen answers one question:

| Place | Question | Who |
|---|---|---|
| Today `/ops` | What needs me this week? | everyone (scoped) |
| Events `/ops/events` | Is each offering ready? | everyone; editors change |
| Tasks `/ops/tasks` | The whole task list | staff |
| Publish `/ops/content` | Is everything we publish moving? | staff |
| Business `/ops/insights` | Is EP healthy? | director |
| People `/ops/team`, Hours `/ops/hours` | Who does what; time worked | staff |
| Settings `/ops/settings` | Every sheet-backed table | director + editors (manager, projects) |
| Landing Pages `/ops/landing` | Is every /lp/ page live and its checkout working? | staff |

## 3. Architecture map

- `app/ops/Shell.js` sidebar + page header (`title`, `eyebrow`, `head`). `lib/ops/nav.js` who sees which item.
- `app/ops/ops.css` the design system. Scoped to `.ops-shell` (and `.ops-login`) because `/teach` reuses `ops-*` class names. Old ops rules in `app/globals.css` are overridden, not yet deleted.
- Tasks: always import from `lib/ops/taskstore.js` (never `motion.js` or `taskdb.js` directly). Shape: `{ id, name, description, due, labels[], completed, blockedOn, auto }`. Owners are labels (a person's name or a role). Conventions kept in `description`: `[ep:EVENTID:task-slug:owner-slug]` event tag, `[blocked:Name]`, `[auto:date:rule]`.
- `lib/ops/tasks.js` task logic (expected tasks from Task Templates, `visibleTo`, `forHome`, `bucket`, `groupByEvent`, `needsOwner`). `syncToMotion()` is a legacy name; it writes to the task store.
- `lib/ops/hours.js` time clock (Neon tables `ops_shifts`, `ops_hour_requests`, `ops_hour_alerts`; made on first use).
- `lib/ops/landingpages.js` + `app/ops/landing/` Landing Pages: reads ep-website's `/api/landing-pages` (5-min cache, `LANDING_PAGES_URL` overrides), derives Upcoming/Running/Ended/Evergreen from `startsAt`/`endsAt` (New York dates), checks each page (must answer 200) and checkout link (2xx) with a 5-min per-instance cache (`?check=1` forces a fresh check), links to the Course Library when the slug matches an offering id. Stores nothing.
- `lib/ops/store.js` the only safe writer to the calendar sheet (by header name, refuses formula columns, conflict check, Change Log). Use it for any sheet write.
- `lib/ops/sitetables.js` + `app/ops/content/SiteEditor.js` the table editor behind Settings (`scope="settings"`).
- `lib/ops/checks.js` + `lib/ops/readiness.js` event readiness checks.
- Crons (`vercel.json`): `/api/ops/daily` 13:00 UTC (task sync, reminders, nudges, Motion digest), `/api/ops/auto` every 15 min (auto-complete, shift sweep).
- Root `ops/` folder (`ops/motion.js`, `ops/tasks.js`) is an old copy, not imported by the app. Confirm and delete.

## 4. Rules (keep these)

- The Google Sheet (EP-Programming-Calendar) is the source of truth for events and settings; the database holds tasks, hours and decisions. Never keep a second checklist.
- Design: terra `--risk` only for late/at risk; pine `--pine` for actions; status is always a dot + a word; 44px rows; one section-header style; underline tabs; detail in a drawer; help text sparingly. No emoji, no new fonts, no gradients.
- Dates are New York time (`todayET()`; `America/New_York` client-side).
- Teacher reminder emails go only to the addresses in that session's Teacher/Host Emails column. Never widen this.
- Automated emails go from "EP Admin" <team@embodiedphilosophy.com>.
- Copy: plain, short, sentence case. Name things the user knows (Master Schedule, Kit, Circle).
- Next.js here is a new major version: check `node_modules/next/dist/docs/` before using unfamiliar APIs.

## 10. YouTube Studio (Nov 2026, branch `claude/youtube-studio`)

Vimeo → YouTube: each Monday the worker (separate repo **embodiedphilosophy/ep-youtube-pipeline**, GitHub Actions)
proposes 5 Studio-Produced talks; staff approve them here; the worker cuts a 15–20 min stretch, makes the thumbnail,
parks the cut on Vimeo; staff review and push to YouTube. Ops only stores, shows and fires.

- Page `/ops/youtube` (`app/ops/youtube/`): tabs This week · Review queue · Published · Skipped. Access `canYouTube` in
  `nav.js` (directors + Team role Media or YouTube, i.e. Jacob and Rebecka). Sidebar: Publishing → YouTube.
- Logic `lib/ops/youtube.js`; records in Neon table `ops_youtube` (`kind` proposal|cut, jsonb `data`; memory without DATABASE_URL).
  Proposal: proposed → producing → ready → published, or skipped. Cut: review ⇄ recutting / rethumbing → publishing → published.
- Worker API `app/api/youtube/*` (Bearer `OPS_PIPELINE_SECRET`, `lib/ops/pipelineauth.js`): `GET /state`, `POST /proposals`,
  `POST /cuts`, `GET /cuts/{id}`, `POST /cuts/{id}/thumbnail` (→ Vercel Blob `youtube/thumbs/`), `POST /cuts/{id}/published`.
  `used_vimeo_ids` = everything approved, skipped, cut or published (untouched proposals may come back).
  `upcoming_programs` = one row per program starting on the Master Schedule in the next 10 weeks.
- A re-cut posts `/cuts` again with the same `proposal_id`: the same cut is updated; any field staff edited (`edited[]`) keeps the staff value.
- Ops fires `repository_dispatch` (`produce`, `thumb`, `publish`) with `GITHUB_PIPELINE_TOKEN`. Re-cut start/end are sent as
  strings because the workflow drops a numeric 0. `thumb` sends the **source** Vimeo ID (the worker grabs frames from it).
- Scheduled release: date + time in New York → `publish_at` in UTC (YouTube keeps it private until then).
- Tasks: one "[yt:week:<date>]" task when proposals arrive and one "[yt:cut:<id>]" per new cut, labelled with directors +
  Media/YouTube people; closed when the week is all decided / the cut is published. Only with the database (not in local tests).
- Env (ep-ops on Vercel): `OPS_PIPELINE_SECRET` (same as the GitHub secret, 24+ chars), `GITHUB_PIPELINE_TOKEN` (fine-grained,
  repo ep-youtube-pipeline, Contents read & write), `BLOB_READ_WRITE_TOKEN` (existing store is fine). Optional
  `GITHUB_PIPELINE_REPO`, `GITHUB_API_BASE` (tests).
- Test: `node scripts/ops-test/youtube.cjs` after `run.sh` (plays the worker; dispatches land in `out/mock.log` as `GITHUB DISPATCH`).

Reads: account (with payment method), pixel (`pixelFiredWithin`), Page, interest search, campaigns, custom audiences, results (`getInsights`: campaign, ad set or ad level, a day at a time, as cents and counts; breakdowns pass straight through). Writes: create campaign, ad set, creative (one per ad: its pictures in the four sizes, or a video, with all five copy sets in an `asset_feed_spec`), ad, image upload; `setStatus` (ACTIVE = Start, PAUSED), `setBudget`; custom audience, hashed-email upload (SHA-256, only counts are ever logged) and lookalike. `buildCampaign(spec)` builds a whole draft paused: a 5 × 5 test is 1 campaign + 5 creatives + 5 ad sets + 25 ads; Advantage+ is 1 ad set with the same 5 ads. PR 2 reuses it.
- **The dry-run rule** (the sign-off box): every write goes through the one function `write()`. Unless `META_ADS_LIVE` is exactly `live` a write does not leave the process: it answers `{ ok: true, dryRun: true, id: 'dryrun-…', would: { method, path, body } }` and logs one line (the kind and path, never the body). Everything is created PAUSED. **Reads** are not gated by the switch (they change and spend nothing) but need `META_ADS_TOKEN`; without it they answer `{ ok: false, notConnected: true }` and make no request.
- **Settings by name, and who adds them** (Jacob or whoever has Vercel admin; the builder never sees the values): `META_ADS_TOKEN` (a Business system user's token with ads_management, ads_read and business_management; kept apart from the Instagram token `META_ACCESS_TOKEN`), `META_AD_ACCOUNT_ID` (act_…), `META_PIXEL_ID`, `META_PAGE_ID`, `META_ADS_LIVE` (leave unset, or anything but `live`, until Jacob says). `META_IG_USER_ID` already exists. `META_CAPI_TOKEN` is not needed yet. **Test-only, never set in production:** `META_ADS_BASE` (points the client at the mock; read only when set) and `ADS_TEST_DB=pglite` (below).
- **Settings › Connections and jobs** has a read-only **Meta ads** row in the systems list (`app/ops/settings/Connections.js`, `metaAdsStatus()`): which of the six settings are in place (names only, never values) and the mode: *Not connected* (no key or no ad account), *Dry run — nothing is sent to Meta*, *Live*. It never calls Meta, so it says "not yet checked with Meta"; real health comes with Connections health. Directors only, like the rest of that group.
- **Tables and store**: `lib/ops/adsstore.js` (one table of columns, `ENTITIES`, drives both the SQL and the code: `createRow`, `getRow`, `listRows`, `updateRow`, `deleteRow`, `campaignTree`) and `lib/ops/adsdb.js` (Neon in production; `query(text, params)`). Twelve tables, all `ads_…`: campaigns (launch link, goal, structure test/advantage, dates that follow the launch, budget, spend cap, Meta settings, draft step, per-campaign rule switches `rules_on` and `rules_dry_run`), adsets (Proven / New test), creatives, copysets (with their source; placeholders block Start), ads, rules (one per campaign: X%, every N hours, Y, ceiling, Z, minimum spend, pause weakest), actions (what each change reversed to: `reverse_to`, `reversed_at`), audiences (standing, tags, overlaps), audience_results (one per audience per campaign), weekly_reads, topic_ideas (a dismissed `topic_key` is never suggested again), and **results**, the one table beyond the design's list: Meta's numbers a day at a time, which the hourly sync writes and the morning rules read. **`ensureAdsTables()` is called by nothing in the app**: PR 2 must call it from Ads pages and from nothing else (`final-sweep.cjs` keeps the two files off the app's import graph until then; PR 2 removes the `ADS_NEXT` line). Merging this creates no tables.
- **Tests without a database**: `@electric-sql/pglite` (devDependency, runs offline, no install scripts) is an in-process Postgres; `ADS_TEST_DB=pglite` makes `adsdb.js` use it and never Neon. It is loaded only by a dynamic import that runs when the switch is set (checked: the production build does not bundle or trace it). PR 2 onwards can start the app with that switch to test Ads pages.
- **The Meta mock** `scripts/ops-test/meta-mock.mjs` (port **4556**, started by `run.sh`, `env.sh` points `META_ADS_BASE` at it and unsets the real Meta settings): account, pixel (fired 2 hours ago), Page, interest search, create/update for every object (refuses anything not PAUSED), a week of results per ad set with return 2.4, 1.8, 1.2, 0.8 and 0.4 (so a rule can raise, hold and turn off), custom audiences and hashed users; `/__log` records every request (never the token), `/__mode?rejectWrites=1`, `/__reset`, `/__state`. Flows: `ads-meta.mjs`, `ads-settings.sh` / `ads-settings.cjs`.
- **Jacob's Ads decisions** (recorded): Ads gets its own sidebar place (PR 2); Ops' own morning job applies the rules, with Reverse links, not Meta's automated rules; Traffic campaigns get no automatic rules; the quiz funnel moves to Ads › Audience insights (PR 5); video ads at 9:16 and 4:5 only. **Make's Ad Agent stays ON**; Ops' rules run as a dry run beside it (`rules_dry_run`) until Jacob says switch. Never both live, or budgets are raised twice.
- **What PRs 2 to 5 build on this**: PR 2 the ads switch on Program › Launch, draft generation, the four editing steps, "Send to Meta, paused" and Start through `buildCampaign` / `setStatus`; PR 3 the hourly results sync (`getInsights` → `results`), the campaign page and the morning rules with Reverse (`actions.reverse_to`), plus the jobs behind `OPS_LIVE` and `META_ADS_LIVE`; PR 4 the audience library (`audiences`, `audience_results`, hashed uploads and lookalikes); PR 5 the weekly read and topic ideas.

PR 2 should confirm them with one paused draft in the real account before anyone presses Start, with Jacob's OK.

## Ads, PR 2: campaign drafts (the ads switch, drafts, the four steps)
The second of five Ads pull requests. It adds the **Ads place** (the ninth, after Publish), the **ads switch** on a launch, **draft generation** and the **four editing steps**. "Send to Meta, paused" and Start exist and work, but with `META_ADS_LIVE` unset (as in production now, with Jake's real token already in Vercel) every Meta write is a dry run.
- **Who sees Ads**: `canAds(user)` in `lib/ops/nav.js` = directors, or anyone with the **Ads** role on the Team tab (Jacob, Rebecka). Nobody else gains it, whatever else they can edit (Floss, Irene, Ichha, Carolyn, Stephanie and teachers are sent away; the API answers 403). Rebecka sees Ads and its results but not Business (Finance, Payroll, Audience) or Settings. Ads has one tab, **Campaigns**; the Audience library and Audience insights tabs arrive with PRs 4 and 5 and are not shown as empty placeholders.
- **The ads switch** (`app/ops/ads/AdsSwitch.js`, used by the Launches wizard's last step and by the launch's own page, so the Program › Launch tab has it): "Run Meta ads for this launch?" Yes / No, the goal (Purchase, Lead, Traffic), the type (Targeting test 5 × 5, Advantage+), the starting budget. Only people who may use Ads see it (the launches API says `canAds`). With it off nothing about a launch changes and no Ads request is made. Saving Yes makes the **draft campaign**; changing the choice on the launch's page changes the draft until it is in Meta; No removes a draft. The Launches list shows a small `Ads · Draft · review` beside a launch that has one. There is **no** sidebar count for Ads drafts (it would read the Ads database on every page; the page-load check keeps those pages free of it).
- **Dates follow the launch** (`lib/ops/adsplan.js`): start is the launch's "doors open" (or two weeks before its day), end is "doors close" (or the day). Whenever a draft is read its dates are brought in line with the launch's key dates; a date a person sets by hand stays until they press "Follow the launch's dates". There is no screen to edit a launch's key dates yet; they move when the Launches row changes.
- **Defaults**: the playbooks carry no ads settings and no new sheet or tab was added. The starting budget by playbook (`BUDGET_BY_PLAYBOOK`: Enrollment $100 a day for a 5 × 5, others $50 to $60, Advantage+ $60) and the rules (`RULE_DEFAULTS`: return 1.5× raise / 1.2× off, cost per lead $1.50 raise / $2.50 off, 20% every 48 hours, ceiling $60, minimum spend $40) are constants in `lib/ops/adsplan.js` and `lib/ops/adsdraft.js`, edited per campaign.
- **The draft pipeline** (`lib/ops/adsdraft.js`, run when the switch is saved and again by **Refresh draft**; what a person edited is remembered in `meta_settings._edited` and never overwritten):
  1. *Link*: the launch's landing page address with `utm_source=meta`, `utm_medium=paid_social`, `utm_campaign=<launch name>`.
  2. *Copy* (`lib/ops/adscopy.js`): five copy sets drafted **only** from the launch's own emails (Email Plan, once they are not the "[FILL IN]" stub), the launch's course page on the Course Pages tab (title, subtitle, summary, what you explore, audience) and real testimonials (Site Testimonials, the program's own and the site-wide ones). Slots: first email, second email, landing page, a testimonial, last email; a gap is filled from what is left over, and a gap with nothing left stays a `[placeholder]`. Every set records `source_kind`, `source_ref` and the words it was drawn from. The model (`ANTHROPIC_API_KEY`, `claude-sonnet-5-5`) is sent only the plain source text: markdown, merge tags, links and email addresses are removed first, and a testimonial's author never leaves the dashboard. Without the key, or if the call fails, every set stays a placeholder and the page says why. A person who writes real words into a placeholder gives it a source (`written`, "Written by <name>"); leaving `[brackets]` in a set makes it a placeholder again. Placeholders block Start (and Send).
  3. *Pictures* (`lib/ops/adsimages.js`): the launch's Course Library cover first, then the best matches in the Drive Image Library's **Art** (no words on the picture, reuse OK, not hidden). Each is read with `readImage` (the same Drive/Make path the social crop tool uses), cut with `sharp` to 9:16 (1080×1920), 4:5 (1080×1350), 1:1 (1080×1080) and 1.91:1 (1200×628), and kept in Vercel Blob (`BLOB_READ_WRITE_TOKEN`). A person can choose another library picture or upload one per ad. A video ad is offered at 9:16 and 4:5 only (one file link each); **videos are not uploaded to Meta from here yet** (a live send refuses and says so).
  4. *Audiences* (`lib/ops/adsaudiences.js`): from the Audience library (`ads_audiences`, empty until PR 4; Proven first with their past result, Retired never), then Meta's interest search from the program's topic, each "New test". A 5 × 5 gets five ad sets; Advantage+ gets one that starts from the interests of the five. A ranked list of others is kept for Swap.
- **The four steps** (`app/ops/ads/Draft.js`, `/ops/ads/[id]?step=1..4`): (1) Audiences, swap from the ranked list, edit name and ages; (2) Creative and copy, the five ads with their crops, the five copy sets and where each came from, button and link, a Feed / Stories preview; (3) Budget (campaign budget or one per ad set, the 5 × 5 default; a lifetime cap), the automatic rules (**stored only**: X% every N hours while return is at least Y or cost per lead at most Y, a ceiling, turn off below Z after a minimum spend, pause the weakest ad after N days; Traffic has none; the switch `rules_on` is stored, `rules_dry_run` stays true; the morning job is PR 3), Meta settings (placements, campaign name; the pixel, Page and Instagram account are shown as set or not, never their ids); (4) Check and start (`lib/ops/adscheck.js`): every ad has all its sizes, no placeholder, the ad link, dates and a budget, **landing page live** (an HTTP check), **pixel fired in the last 24 hours**, **ad account has a payment method**. Switching 5 × 5 ↔ Advantage+ keeps the pictures, words and rules and changes only the audiences (budgets are re-spread over the ad sets).
- **Send and Start** (`lib/ops/adssend.js`): "Send to Meta, paused" needs the content to be complete (pictures, words, audiences, link; the landing page, pixel and payment method are Start's checks), uploads each picture, then `buildCampaign` makes everything PAUSED (1 campaign, 5 ad sets, 5 creatives, 25 ads). Start needs every check and, when live, a campaign already sent paused; it turns on the campaign, each ad set and each ad (31 for a 5 × 5). Both need a person to press the button and confirm. **With `META_ADS_LIVE` unset both are dry runs** (the page says "Dry run — nothing was sent to Meta" and lists what would have been sent: the names, counts, budget, dates, link and audiences); the Meta mock's write log stays empty. A campaign in Meta is read-only here. A send that stops part-way records what Meta made so it can be removed by hand.
- **Tables**: `adsTablesExist()` (new in `lib/ops/adsstore.js`) lets Ads pages read without making anything; the tables are made by the first thing someone saves (the switch). Only Ads code imports the store (`ads-settings.cjs` checks); PGlite is loaded by a name held in a variable so the build neither bundles nor traces it.
- **Test-only switches (all inert unless set, none set in production)**: `ANTHROPIC_BASE` (points the drafting call at the mock), `ADS_TEST_BLOB=inline` (pictures kept inline when there is no Blob token), plus PR 1's `META_ADS_BASE` and `ADS_TEST_DB=pglite`. `env.sh` sets the first two and unsets the real Anthropic key.
- **What PRs 3 to 5 build on this**: PR 3 the hourly results sync, the live campaign page (what the Ad Agent did today, Reverse links) and the morning rules reading `ads_rules`; PR 4 the audience library (`ads_audiences` feeds the suggestions above); PR 5 the weekly read and topic ideas. Ads PR 3 should also show the Ads sidebar count once there is something to count.
- **Not verified against the real Meta or Anthropic** (mock only): the shape Meta accepts for a creative with five texts and four sizes, the ad set targeting fields (interests, Advantage+ audience, placements), budget and cap units, the start and end time format (New York offset), the picture upload response (`images.<name>.hash`), and the model id and answer format. The follow-up is one paused draft in the real account, with Jake's OK, before anyone presses Start. The preview is an approximation of Meta's, not Meta's own.

## Ads, PR 3: live campaigns and rules (results sync, campaign page, morning rules with Reverse, daily digest)
The third of five Ads pull requests. It adds the hourly results sync, the live campaign page, the morning rules with Reverse and the daily ad digest. **With `META_ADS_LIVE` unset and Make's Ad Agent still on (today), everything the rules do is a dry run: nothing is changed in Meta.**
- **The hourly results sync** (`/api/ops/ads-sync`, `vercel.json` at :10, `lib/ops/adssync.js`): for every campaign sent to Meta (paused, running or paused again) it reads results through the client (`getInsights`, ad set level and ad level, last 7 days, `?days=N` up to 60) and upserts them into `ads_results`, one row per day per ad set (and per ad), under Ops' own ids (`ON CONFLICT` on the table's unique index, so running it twice changes nothing). It **only reads** (needs `META_ADS_TOKEN`, never the safety switch; no token or no campaigns = does nothing). A Meta error or rate limit is written on the campaign (`meta_settings.sync`, shown on its page) and the job carries on. Gated by `OPS_LIVE` like the other jobs (`skipped` without it); `?dry=1` reads and reports without keeping anything. It is in Settings › Connections and jobs ("Ad results").
- **The campaign page** (`/ops/ads/[id]`, `app/ops/ads/Live.js`; the same address shows the draft steps while it is a draft, `?step=1..4` shows them read-only afterwards): status, spend so far against the lifetime cap, results per ad set (budget, spend, return on ad spend or cost per lead, purchases or leads, a three-day trend, status) with the five ads under each, the rules in force in plain English with the **"Apply these rules each morning"** switch (default off; saved by a person, any stage), **"What the Ad Agent did today"** with Reverse, earlier changes, and **Pause / Start again** (a person, a confirm, through the write gate; a campaign in Meta's draft steps can still be started from here). Ads › Campaigns gets the Live filter, spend and last-three-days columns and the same "What the Ad Agent did today" (with Reverse). **There is no sidebar count for Ads**: it would read the Ads database on every page; the page-load check keeps other pages free of it.
- **The morning rules** (`/api/ops/ads-rules`, daily 13:30 UTC about 9 am New York, `lib/ops/adsrules.js`): first a sync, then, for each **running** campaign whose rules a person switched on (never Traffic), each ad set is judged on the **average of the last 72 hours** (the three full days before today, from `ads_results`): *turn off* when return on ad spend is below Z (cost per lead above Z) once it has spent the minimum (lifetime spend); else *raise* the daily budget by X% when return is at least Y (cost per lead at most Y), no more often than every N hours (a daily job counts 46 as 48), never above the ceiling (a per-ad-set ceiling on the ad set beats the campaign's); else *hold*. Optional: after N days of results, pause the weakest ad in each ad set that stays on (once per set, only where the ad is clearly worse than the next). Campaigns with one shared budget are only turned off, never raised (Meta moves that money itself). **Every decision, holds included, is a row in `ads_actions`**: from, to, what Reverse restores, applied or dry run, and the reason with the numbers. Running it twice in a morning does nothing more. A person who reverses a turn-off gives the ad set three more days before the rules judge it again; a raise somebody changed in Meta by hand is not raised again (the rules read Meta first and hold).
- **THREE LOCKS: a change reaches Meta only when all three are open.** (a) the jobs are live on this project (`OPS_LIVE=1`); (b) the Meta safety switch (`META_ADS_LIVE=live`; every change also goes through the one write gate in `meta-ads.js`); (c) **Make's Ad Agent is OFF**: the Mode on the Ad Agent tab of the Revenue & Metrics sheet (the cell Today and Finance already read; the job reads it fresh, the campaign page reads it fresh when it opens, the list uses the cached read). Anything but OFF, or a cell Ops can't read, counts as on. With any lock closed the same decisions are made and recorded as dry runs, and the page says why (for example "Dry run — Make's Ad Agent is still on, so nothing was changed"). `?dry=1` on the route previews without recording. This PR **never writes to the Revenue & Metrics sheet** and never touches Make: Make still writes ad spend there, and Ops writing it too would double count. **"Ads keeps writing spend there" belongs to the pull request that switches Make off.** The campaign's `rules_dry_run` column is not used (the three locks decide).
- **How Jacob switches Ops' rules live, safely**
  1. Switch the campaign's rules on ("Apply these rules each morning"). While Make's Ad Agent is on this is safe: Ops only records what it would have done. Watch Ops' dry-run actions beside Make's for a while (the page, Ads › Campaigns and the daily digest) and see whether you agree with them.
  2. When you do, turn Make's Ad Agent scenarios off in Make.
  3. Set the Ad Agent Mode to OFF on the Ad Agent tab of the Revenue & Metrics sheet.
  4. Set `META_ADS_LIVE=live` in Vercel (this also lets Send, Start, Pause and Reverse reach Meta).
  5. The next morning the rules change Meta for every campaign whose rules are switched on, and the digest lists each change with its Reverse link. To stop, switch a campaign's rules off, or set the Mode back to anything but OFF.
- **Reverse** (a person; a confirm; through the write gate): on an applied change on the campaign page, on Ads › Campaigns, and by the digest's link (`/ops/ads/<id>#change-<id>`, which opens the page at that change: the link itself never reverses). It puts the earlier budget back or switches the ad set or ad back on, in Meta and in Ops, marks the change reversed by whom, and records a reversing action. It is **idempotent** (the second press says already reversed and writes nothing) and **refuses plainly** if the value was changed again since, in Ops or in Meta (it reads Meta first). A dry-run action has no Reverse. With the switch off, Reverse is a dry run. A Meta that refuses a rule's change is recorded as "didn't go through" with the reason; nothing is marked changed and it is not retried that morning.
- **The daily ad digest** (`lib/ops/adsdigest.js`, built after the rules and sent through the same Resend mail as the other digests): to directors and people with the Ads role who have an address on the Team tab, only when there is something to report (a running campaign spent yesterday, or a change was made or would have been). Per campaign: yesterday's spend and return, what the rules did (or "(Dry run, nothing changed)"), with Reverse links at the final addresses. `?dry=1` (and `&html=1`) previews it; tests never send (no mail key in the test kit).
- **Test-only switches**: none new. The test kit adds `failInsights` to the Meta mock and uses the earlier `ADS_TEST_DB=pglite` and `META_ADS_BASE`. No new production environment variable.
- **Not verified against the real Meta or Make**: the insights field names and the action types read as purchases and leads (`purchase`, `lead`, with `omni_` variants), that ad level results carry `ad_id`, the real shape of the rate-limit error codes (4, 17, 32, 613 are taken as "slow down"), that reading `daily_budget` and `status` of an ad set or ad by id works with this token, that a budget change by `POST <ad set id>` takes `daily_budget` in cents, and whether Make's Ad Agent really stops when its scenarios are off and the Mode is OFF (Ops reads only the Mode). The sheet is read for the Mode only. Nothing was run against the real Meta, Make, Neon or Resend. The Ads list's Live view and the digest have only seen mock data.
- **What PRs 4 and 5 build on this**: PR 4 the audience library (standing from `ads_audience_results`, `ads_results` feeds it); PR 5 the weekly read and topic ideas.
